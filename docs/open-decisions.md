# Open decisions and proposals

Working list of decisions that must be made before or during each phase. Reviewed and agreed as
the design direction on 2026-11-05. Each entry has a proposal
optimised for: zero or near-zero cost first, then simplicity, without giving up security or
consistency. When an entry is accepted it becomes an ADR in `decisions.md` and is marked here as
`Accepted (ADR yyyy-mm-dd)`. Numbers correspond to the review of 2026-11-05.

Already accepted on 2026-11-05, pending ADR text:

- Secrets: Google Secret Manager as the only secret store; identity federation everywhere
  (ADC locally, service account on Cloud Run, Workload Identity Federation on GitHub Actions);
  no service-account JSON keys; Terraform creates secret containers, never versions.
- Cadence: Twitch and Kick every 15 minutes, Steam players every 30 minutes.

## Phase 1: Twitch to BigQuery with one live chart

### 1. Twitch sampling universe

Proposal: two tiers in one job run.

- Tier A: page `GET /streams` (all games, sorted by viewers) until `viewer_count < 10`.
  Roughly 100 pages, well under the 800 points/min limit.
- Tier B: `GET /streams?game_id=...` for the watchlist (up to 100 game ids per call), with no
  viewer floor. Watchlist = Steam releases of the current and previous week plus games under
  manual follow-up.

Store one row per stream. Streams under 10 viewers outside the watchlist are not captured; this
bias is documented in the data contract. Estimated volume: 8-12k rows per run, 1M rows/day,
5-6 GB/month logical. Rejected: `GET /games/top` only (misses small games, which are the
project's question); storing only per-game aggregates (loses per-channel analysis and the
ability to redefine metrics later).

### 2. Data contract: `audience_sample` v1

Three event types, each its own topic, Avro schema and raw table:

- `audience_sample` (Twitch, Kick): `schema_version`, `source`, `sampled_at` (15-min bucket,
  UTC), `observed_at`, `run_id`, `platform_game_id`, `platform_game_name`, `channel_id`,
  `channel_login`, `stream_id` (nullable), `stream_started_at`, `viewer_count`, `language`.
- `player_sample` (Steam): `schema_version`, `sampled_at`, `observed_at`, `run_id`, `appid`,
  `player_count`.
- `review_snapshot` (Steam): `schema_version`, `snapshot_at`, `observed_at`, `run_id`, `appid`,
  `total_reviews`, `total_positive`, `total_negative`, `review_score`.

Adapters emit platform ids only; cross-platform resolution happens in dbt. Dedupe key:
(`source`, `channel_id`, `sampled_at`) for audience, (`appid`, `sampled_at`) for players,
(`appid`, `snapshot_at`) for reviews. Stream titles and tags are out of v1 (30 % of row size,
no planned use). Schemas live in `contracts/` and are the single source for Terraform (topic
schema), BigQuery table definitions and Python validation; a unit test asserts they agree.

### 3. Canonical game key

IGDB id is canonical. `dim_game` in dbt joins IGDB `external_games` (category 1 = Steam appid,
category 14 = Twitch game id). Kick categories have no external ids: a dbt seed
`kick_category_map.csv` holds `kick_category_id -> igdb_id`, generated by a name-matching script
and reviewed by hand before commit. Unmapped rows stay in staging with a null `igdb_id` and are
counted in a data test.

### 4. Pub/Sub and BigQuery raw layout

Per event type: one topic with Avro schema, one BigQuery subscription with "use topic schema" and
`write_metadata = true`, one dead-letter topic with its own BigQuery subscription so rejected
messages are queryable. Raw tables partitioned by day on `sampled_at`, clustered by
(`source`, `platform_game_id`), `require_partition_filter = true`. No partition expiration
(see 23). Rejected: single JSON column (validation would move into dbt and schema drift would be
silent).

### 5. Project, region, Terraform bootstrap

One GCP project, one environment. Region `us-central1` for Cloud Run, Scheduler, Artifact
Registry and the BigQuery datasets (regional dataset, same storage price as multi-region, fewer
cross-location surprises). `terraform/bootstrap.sh` run once by hand: enable APIs, create the
state bucket with versioning and uniform access; everything else in Terraform. One service account
per job with publisher rights on its topic and accessor rights on its secret only; the default
compute service account is not used. "Dev" is a `--dry-run` flag on the adapters that prints
events instead of publishing, plus the dbt dev target (16); no second project or topics.

### 6. Repository visibility and license

Public from the first push; MIT license. Enable secret scanning with push protection and branch
protection on `main` requiring the CI check. Dashboard shared as a public Looker Studio link
backed by small mart tables (17).

### 7. Build and deploy

One Python package, one Docker image, N Cloud Run jobs that differ only in the entrypoint argument
(`twitch`, `kick`, `steam-players`, `steam-reviews`, `igdb`, `dbt`). GitHub Actions on push to
`main`: build, push to Artifact Registry (regional, cleanup policy keeps the last 3 images,
within the 0.5 GB free tier), `gcloud run jobs update --image`. Authentication through Workload
Identity Federation restricted to this repository and the `main` branch. Rejected: source deploy
with buildpacks (slower, less reproducible); Cloud Build triggers (a second CI system).

### 8. Python tooling

Python 3.12, `uv` for dependencies and lockfile, `ruff` for lint and format, `pytest`. API
responses recorded once as JSON fixtures under `ingestion/tests/fixtures/`; tests never call live
APIs. `pre-commit` with `ruff` and `gitleaks`. No type checker in v1.

### 9. Failures, idempotency, alerting

Scheduler triggers the job; job `max_retries = 1`, task timeout 5 minutes. `sampled_at` is the
15-minute bucket computed from the current time; a retry inside the same bucket may duplicate
rows, and staging deduplicates with `row_number()` over the dedupe key. Adapters honour
`Ratelimit-Remaining` headers, back off, and end the run early with a logged partial-run marker
rather than failing. Alerting: a log-based metric on failed executions with a Cloud Monitoring
email policy, plus dbt `source freshness` so a silent gap is caught within one dbt run. All free.

### 10. Time conventions

UTC everywhere. `sampled_at` is the bucket, `observed_at` the request time. Daily aggregates use
UTC days. Steam release timestamp (`t0`) is inferred as the first `player_sample` with
`player_count > 0` on or after the store release date; the store date at 00:00 UTC is the
fallback. The inference rule is part of the target definitions (18).

## Phase 1b: Kick, Steam, IGDB, dbt, dashboard

### 11. Steam universe

Two feeds:

- Top: `ISteamChartsService/GetMostPlayedGames/v1`, one call every 30 minutes, top 100 with
  current and peak players. Target 4 is redefined to "enters the top 100" (see 18).
- Watchlist: daily `IStoreService/GetAppList` with `if_modified_since` (requires a Steam Web API
  key, the third and last secret), then `appdetails` only for new or changed appids, paced at
  about one request per 1.5 s. Apps with `type = game` and a release date within -7 / +14 days
  join the watchlist. Watchlist games are polled with `GetNumberOfCurrentPlayers` every 30
  minutes.

IGDB remains metadata enrichment, not the release source (its coverage of small Steam releases is
incomplete). Rejected: scraping the store (fragile, terms of service); SteamSpy (unofficial).

### 12. Review cadence

An hourly Steam reviews job queries `appreviews?json=1&num_per_page=0&language=all&purchase_type=all`
for watchlist games with `t0` less than 72 hours ago, and a daily pass for the rest of the
watchlist. Roughly 720 Secret Manager reads per month.

### 13. Historical review backfill

The reviews endpoint paginates with a cursor and every review carries `timestamp_created`, so the
review curve of any released game can be reconstructed. Proposal: a one-off local run (ADC,
checkpoint file, publishes to the same `review_snapshot` topic with a `source = backfill` flag)
over games released in the previous 24 months, storing per-game per-day counts only, never review
text. Estimated 150-250k requests over two or three days at one request per second. This gives
Phase 2 a training set with known outcomes from week 1 instead of week 13. Concurrent-player
history has no official equivalent and is not backfilled.

### 14. Kick

`GET /public/v1/livestreams?sort=viewer_count&limit=100` has no pagination, so the universe is the
top 100 overall plus one call per watchlist category (`category_id`), category ids resolved
through `GET /public/v1/categories?q=`. App access token obtained per run with client
credentials. Stream end is inferred in dbt: a (channel, `stream_started_at`) pair is closed when
absent from two consecutive samples. Rate limits are not documented; the adapter uses a fixed
pace and backs off on 429.

### 15. IGDB

Daily job, same Twitch credentials. Queries `games` and `external_games` only for Twitch game ids
seen in the last 24 hours that are missing from `dim_game`, plus watchlist appids. 500 ids per
query, 4 requests per second limit, a few dozen requests per day.

### 16. Where dbt runs

`dbt-core` with `dbt-bigquery` inside the same image, as a Cloud Run job every hour after the
ingestion ticks. Incremental models over the last two days of partitions. Targets: `prod`
(service account) and `dev` (ADC, dataset `dev_<user>`, same raw sources). CI runs
`dbt build --empty` plus unit tests against the `ci` dataset, which validates SQL at zero scan
cost. Rejected: dbt Cloud (second platform); BigQuery scheduled queries (no tests, no lineage).

### 17. Query cost control

Marts are materialised tables sized for the dashboard; Looker Studio connects only to marts, with
a default date range of 30 days. `require_partition_filter` on raw and intermediate tables.
BigQuery custom daily query quota of 50 GB per project as a hard stop. Budget alerts at 5 and
10 USD. Billing export to a BigQuery dataset feeds a `cost_daily` mart and a dashboard page; this
replaces a hand-written cost log.

## Ledger and Phase 2

### 18. Target definitions (`forecasts/targets.md`)

- T1a `peak_30d`: max `player_count` over samples in [`t0`, `t0` + 30 d). Forecast at
  `t0` + 72 h using data strictly before that instant.
- T1b `reviews_30d`: `total_reviews` of the first snapshot at or after `t0` + 30 d.
- T2 `reaches_N_90d`, N in {10, 100, 1000}: `total_reviews` at the first snapshot at or after
  `t0` + 90 d is at least N. Forecast on the Monday before release.
- T3 `half_life_days`: days from the peak day to the first day whose daily peak is below half of
  `peak_30d`; horizon 90 days; right-censored if not reached.
- T4 `breakout_7d`: a watchlist or recent-release game absent from the top 100 at week start that
  appears in it within 7 days.
- T5 `nowcast_next_day_peak`: next UTC day's Steam daily peak from today's Twitch and Kick hours
  watched, distinct channels and today's players; baseline persistence.

### 19. Comparables

Pre-launch: games from the backfill (13) released in the last 24 months, same price band
(free / under 10 / 10-25 / over 25 USD), same early-access flag, ranked by Jaccard similarity of
Steam tags; the 50 nearest form the set. Baseline = median and 10th/90th percentiles of the target
in that set. Post-72 h targets scale the set by the median ratio `peak_30d / peak_72h`. Nowcast
baseline = persistence.

### 20. Ledger mechanics

Table `forecasts.ledger` in BigQuery plus `forecasts/ledger/YYYY-WW.csv` committed every Monday
and tagged `ledger/YYYY-WW`; the commit records the SHA-256 of the file. The GitHub commit and
tag timestamps are the pre-registration evidence. Outcomes and scores are appended as rows by a
dbt model, never by editing the forecast row. Ledger universe: watchlist games with a store
release date in the coming Monday-Sunday window.

### 21. Evaluation metrics

Continuous targets: pinball loss at q10/q50/q90, coverage of the 80 % interval, mean absolute
error in log10, skill score `1 - model / baseline`. Binary target T2: Brier score, calibration
plot, baseline event rate. All fixed in `forecasts/targets.md` before the first ledger row.

### 22. Analysis note template

`analysis/TEMPLATE.md`: metadata (date, commit, data snapshot date range) and the five sections:
question, data, method, result with uncertainty, decision it informs. Notes are Markdown with
figures as PNG under `analysis/<slug>/`; supporting code is a plain Python script in the same
folder.

### 23. Retention

No partition expiration. Raw datasets use physical (compressed) storage billing, which is several
times cheaper than logical billing for narrow repetitive rows. Revisit when raw storage passes
50 GB. Daily game-level aggregates are kept indefinitely regardless.
